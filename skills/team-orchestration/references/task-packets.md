# 任务包构造规范

派发任何子 agent 前，把任务构造成一个**自包含的任务包**。子 agent 是 fresh context，它只知道你写进任务包的内容。

## 结构

每个任务包必含四要素：

```
## 目标
要完成什么，一两句话。动词开头。

## 约束
硬性边界：语言/框架版本、不能动的文件、必须保持的接口、风格规则、
依赖白名单。没有就写「无特殊约束」。

## 相关文件
精确路径清单（含行号或函数名锚点更好）。只列真正相关的，
不要用 glob 把半个仓库扫进去。子 agent 需要更多上下文时让它自己
用 read/grep 探索——探索是廉价的，把整个文件树塞进任务包是昂贵的。

## 验收标准
可机械判定的完成条件：跑什么命令、期望什么输出、哪些测试必须通过。
```

## 规则

1. **禁止粘贴对话历史**。用户的原话、你的思考过程、之前的往返，都不进任务包。任务包是蒸馏产物，不是转发。
2. **禁止「帮我做 X」式的模糊任务包**。X 没法拆成四要素时，说明还没到派发时机——你先设计。
3. **文件路径优先于内容摘录**。让子 agent 自己读文件，只摘录关键的接口签名/约束片段（<20 行）。
4. **一个任务包一个焦点**。同文件的两个独立改动拆成两包；同构批量改动（如「给这 10 个文件加同一类错误处理」）合一包并行派。
5. **研究任务包**要给：具体问题列表（可枚举）、背景（为什么问，<100 字）、期望的简报重点。
6. **challenge 任务包**要给：设计文档全文（这是审查对象，允许完整给出）、决策上下文摘要（为什么这么做，关键取舍）、明确请它审查的维度。
7. **评审任务包**（给 reviewer）要给四样：
   - **被评审的任务包原文**（对照基准，评审「计划对齐」靠它）
   - **执行者汇报全文**（执行摘要 + 变更清单 + 验证结果 + 上报项）
   - **查看变更的方式**：git 范围（BASE_SHA..HEAD_SHA，需 executor 先 commit）或精确的文件清单；未提交改动给 `git diff` 工作区说明
   - **重点审查维度**（可选）：如安全、并发、边界——默认全维度
   不要把 diff 本体粘进任务包；让 reviewer 自己用只读 git 命令看，任务包只给定位方式。

## 反例

❌ 坏任务包：
> 用户反馈登录有 bug，请修复。以下是完整对话记录：（3000 字转储）

✅ 好任务包：
> **目标**：修复 `src/auth/login.ts` 中 session 过期后仍返回 200 的问题。
> **约束**：不改 `SessionStore` 公开接口；TypeScript strict 模式必须编译通过。
> **相关文件**：`src/auth/login.ts`（`verifySession` 函数，约 L45–80）、`src/store/session.ts`（只读参考）。
> **验收标准**：`npm test -- auth` 全绿；新增一个过期 session 返回 401 的用例。
